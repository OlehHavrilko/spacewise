# ADR 0005. Шифрование путей в локальных базах: DPAPI по полям или шифрование всей БД

- Статус: предложено (по результатам spike)
- Дата: 2026-10-23
- Закрывает: Q16 из §16 ТЗ (`docs/spec/ТЗ Spacewise.md`); связано с Q14 (ADR 0006)
- Код spike: `spikes/Storage/` (консольные проекты, в `Spacewise.slnx` не входят)

## Контекст

§8 ТЗ хранит дерево путей в `cache.db` в таблице `paths(id, parent_id, name)` с пометкой «имена зашифрованы DPAPI при at-rest режиме». В разделе о приватности сказано: «Поля с путями шифруются DPAPI (`ProtectedData`, CurrentUser); SQLCipher — альтернатива, решение в ADR». В таблице угроз строка «Утечка путей» закрывается DPAPI, логами без путей и опцией «Скрыть пути» в экспорте. `journal.db` (план, действия, карантин, решения) тоже содержит пути и ценнее `cache.db`: её нельзя восстановить пересканированием.

Имена файлов и папок раскрывают много: имена проектов, клиентов, медицинские и юридические документы, игры, ПО. Поэтому само шифрование под вопросом не стоит. Вопрос в том, на каком уровне шифровать и какой ценой.

### Модель угроз

| Угроза | Что защищает уже сейчас | Что добавляет шифрование |
|---|---|---|
| Другой локальный пользователь без прав администратора | ACL `%LOCALAPPDATA%\Spacewise` на текущего пользователя | Глубокую оборону на случай ошибки в ACL или копирования файла в общую папку |
| Кража диска или ноутбука, офлайн-доступ без BitLocker | Ничего | Ключ обёрнут DPAPI, мастер-ключ DPAPI выводится из пароля пользователя. Стойкость равна стойкости пароля. При включённом BitLocker выигрыш небольшой |
| Резервная копия, облачная синхронизация профиля, support bundle | «Скрыть пути» в экспорте, логи без путей | Копия `*.db` без ключа бесполезна. Ключ в бандл не попадает никогда |
| Вредоносный код в сессии пользователя | Ничего | Ничего. Любой процесс пользователя может вызвать `ProtectedData.Unprotect`. Это осознанный non-goal |
| Администратор машины | Ничего | Почти ничего: администратор может внедриться в сессию пользователя. Non-goal |

## Варианты

1. **DPAPI по полям.** Каждое `paths.name` (и пути в `journal.db`) хранится как blob `ProtectedData.Protect(utf8, entropy, CurrentUser)`.
2. **Конверт: AES-GCM по полям, ключ обёрнут DPAPI.** Один случайный 256-битный ключ, `ProtectedData` вызывается один раз при старте. Поля шифруются `AesGcm` (nonce 12 B + tag 16 B). Для поиска по равенству добавляется blind index: `HMAC-SHA256(key2, normalize(name))`, усечённый до 16 B.
3. **Шифрование всей БД (SQLCipher-совместимый codec).** Страницы БД и WAL шифрует нативная библиотека. Ключ БД случайный и обёрнут DPAPI, как в варианте 2. Кандидаты:
   - `SQLitePCLRaw.bundle_e_sqlcipher` (SQLCipher community в сборке SQLitePCLRaw);
   - официальный SQLCipher for .NET от Zetetic (коммерческая лицензия);
   - `SQLite3MC.PCLRaw.bundle` (SQLite3 Multiple Ciphers: ChaCha20-Poly1305, AES-256, совместимость с форматом SQLCipher и др.).
4. **Без шифрования**, только ACL и BitLocker. Это базовая линия для сравнения.

## Измерения

Машина: та же, что в ADR 0001 (Windows 10.0.26300, процесс без повышения прав), .NET SDK 10.0.402, Release. Запуск: `dotnet run --project spikes/Storage/<Variant> -c Release [-- --dpapi]`. БД создаются во временной папке `%TEMP%\spacewise-probe-<guid>`, которая удаляется после прогона.

### Нативный SQLite и шифрование

| Вариант (проект) | Пакеты | `sqlite_version()` | ≥ 3.51.3 | WAL / `synchronous=FULL` | Шифрование |
|---|---|---|---|---|---|
| `Default` | `Microsoft.Data.Sqlite` 10.0.13 → транзитивно `SQLitePCLRaw.bundle_e_sqlite3` 2.1.13 | 3.53.3 | да | `wal` / 2 | нет (`Password` → `InvalidOperationException`) |
| `Pcl2Latest` | + `SQLitePCLRaw.bundle_e_sqlite3` 2.1.14 | 3.54.0 | да | `wal` / 2 | нет |
| `Pcl3` | `Microsoft.Data.Sqlite.Core` 10.0.13 + `SQLitePCLRaw.bundle_e_sqlite3` 3.0.5 (тянет пакет `SQLite` 3.53.4) | 3.53.4 | да | `wal` / 2 | нет |
| `Mc` | `Microsoft.Data.Sqlite.Core` 10.0.13 + `SQLite3MC.PCLRaw.bundle` 2.6.1 (тянет `SQLitePCLRaw.core` 3.0.2) | 3.54.0 | да | `wal` / 2 | да |
| `SqlCipher` | `Microsoft.Data.Sqlite.Core` 10.0.13 + `SQLitePCLRaw.bundle_e_sqlcipher` 2.1.11 | **3.39.2** | **нет** | `wal` / 2 | да, `cipher_version` = `4.5.2 community` |

Во всех вариантах `compile_options` содержит `THREADSAFE=1`, `ENABLE_FTS5`, `ENABLE_RTREE`, `ENABLE_MATH_FUNCTIONS`, `DEFAULT_FOREIGN_KEYS`. У `Mc` и `SqlCipher` `TEMP_STORE=2` (временные таблицы в памяти), у e_sqlite3 `TEMP_STORE=1`.

Проверка шифрования для `Mc` и `SqlCipher`: заголовок файла не начинается с `SQLite format 3`, неверный ключ отклоняется (`SqliteException`), строка `file_0` из вставленных имён не находится ни в `-wal` до checkpoint, ни в основном файле после `wal_checkpoint(TRUNCATE)`. В незашифрованной БД та же строка находится в обоих файлах.

Вставка 100 000 строк `paths` одной транзакцией, WAL, `synchronous=FULL`:

| Вариант | Без ключа | С ключом |
|---|---|---|
| `Default` | 175–214 мс | — |
| `Mc` | 180–183 мс | 152–169 мс |
| `SqlCipher` | 182–187 мс | 194–198 мс |

Разница в пределах шума: при 100k коротких строк данные почти целиком в page cache, шифруются только записываемые страницы. Нагрузку на чтение больших БД этот тест не показывает (см. «Что не проверено»).

### Стоимость шифрования по полям (N = 100 000, `DataProtectionScope.CurrentUser`)

| Операция | Полный путь (в среднем 84 B UTF-8) | Только имя (в среднем 16 B) |
|---|---|---|
| `ProtectedData.Protect` | 20 668 мс (206,7 мкс/поле) | 21 191 мс (211,9 мкс/поле) |
| `ProtectedData.Unprotect` | 15 994 мс (159,9 мкс/поле) | 15 912 мс (159,1 мкс/поле) |
| Размер blob DPAPI | 307 B (+222 B) | 238 B (+222 B, ×15) |
| `AesGcm` encrypt / decrypt, ключ обёрнут DPAPI | 58 / 32 мс | 24 / 40 мс |
| Размер AES-GCM | +28 B/поле | +28 B/поле |
| `HMACSHA256` blind index | — | 46 мс, 32 B (или 16 B усечённый) |
| Обёрнутый DPAPI 256-битный ключ | 262 B, один раз | |

DPAPI по полям стоит около 0,2 мс на вызов независимо от длины. Причина в том, что каждый вызов идёт через LSA (RPC, вывод ключа из мастер-ключа). Скан тома на 1–3 млн элементов потребует 3,5–10 минут только на `Protect`. Открытие дерева на 100k узлов займёт около 16 с на `Unprotect`. Накладные расходы по месту: +222 B на каждое имя, то есть таблица `paths` вырастает примерно в 10–15 раз.

### Влияние на запросы

| Возможность | DPAPI / AES-GCM по полям | Шифрование всей БД |
|---|---|---|
| Навигация по дереву (`parent_id`) | да | да |
| Точный поиск пути | только через blind index по каждому компоненту | да |
| Префиксный поиск, `LIKE`, регистронезависимый фильтр в UI | нет | да |
| `ORDER BY name`, FTS5 по именам | нет | да |
| Индексы по имени | только по HMAC | да |
| Структура дерева, размеры, даты, число файлов | открыты | зашифрованы |

Шифрование по полям оставляет открытыми всю структуру (глубина, число детей, размеры, даты) и все остальные таблицы (`findings.evidence_json`, `journal.db`). Чтобы закрыть их, шифровать пришлось бы почти каждый столбец. Оставлять имена папок открытыми и шифровать только имена файлов бессмысленно: имена папок раскрывают не меньше (`Клиент Иванов`, `Diagnoses`).

### Лицензии

| Компонент | Лицензия | Сопровождение |
|---|---|---|
| `SQLite3MC.PCLRaw.bundle` (SQLite3 Multiple Ciphers, utelle) | MIT; ядро SQLite — public domain | живой: 2.6.1 от 2026-10-12, SQLite 3.54.0 |
| `SQLitePCLRaw.bundle_e_sqlcipher` | Apache-2.0 (обёртка); SQLCipher community — BSD-style | последний релиз 2.1.11 от 2025-03-07, в линейке SQLitePCLRaw 3.x пакета нет; внутри SQLite 3.39.2 |
| SQLCipher for .NET (Zetetic) | коммерческая | живой, платный; для бесплатного продукта не подходит без бюджета |
| `System.Security.Cryptography.ProtectedData` | MIT | часть .NET 10.0.13 |

## Решение

**Шифровать БД целиком через SQLite3 Multiple Ciphers (`Microsoft.Data.Sqlite.Core` + `SQLite3MC.PCLRaw.bundle`). Ключ случайный, 256 бит, на каждую БД свой. Ключ хранится обёрнутым DPAPI CurrentUser. DPAPI по полям не используем.**

Обоснование:

1. DPAPI по полям непригоден по производительности (около 0,2 мс на поле, минуты на скан тома) и по месту (+222 B на имя). Он ломает поиск и сортировку, а структуру дерева оставляет открытой.
2. Конверт с AES-GCM по полям быстрый, но запросы ломает так же. Пришлось бы шифровать почти все столбцы обеих БД и поддерживать blind index. Сложность высокая, защита при этом неполная.
3. Шифрование всей БД закрывает все таблицы, WAL и индексы. SQL и FTS сохраняются, накладные расходы на запись в пределах шума. SQLite3MC — единственный найденный бесплатный (MIT) и сопровождаемый вариант, который проходит требование ТЗ SQLite ≥ 3.51.3 (у него 3.54.0). `bundle_e_sqlcipher` отклонён: SQLite 3.39.2 не проходит требование по исправлению WAL-reset, пакет заброшен.
4. Пометку «at-rest режим» из §8 предлагается заменить на «шифрование всегда включено». Оно почти бесплатно, а отдельный режим удваивает число путей кода и тестов.

### Управление ключом

- При первом запуске создать `key = RandomNumberGenerator.GetBytes(32)` отдельно для `cache.db` и для `journal.db`.
- Сохранить `ProtectedData.Protect(key, entropy: "Spacewise/<db>/v1", CurrentUser)` в `%LOCALAPPDATA%\Spacewise\keys\<db>.key` (ACL как у БД) и рядом версию формата.
- Передавать ключ в SQLite3MC как raw-ключ (`PRAGMA key = "x'<hex>'"`) сразу после `Open`, а не строкой `Password` в connection string: строка подключения живёт в пуле. Шифр зафиксировать явно (`PRAGMA cipher = 'chacha20'` или `sqlcipher`), не полагаться на значение по умолчанию.
- Обнулять буфер ключа после установки (`CryptographicOperations.ZeroMemory`).
- Ключи и `*.key` никогда не попадают в support bundle, логи и экспорт. Это отдельный тест на support bundle.
- Ротация: `PRAGMA rekey` с новым ключом и перезапись `*.key` атомарно (temp + `MoveFileEx`). В MVP не нужна.

### Восстановление при потере ключа

DPAPI CurrentUser перестаёт расшифровывать в нескольких случаях: профиль пересоздан, пароль локальной учётной записи **сброшен** администратором (обычная смена пароля DPAPI не ломает), БД перенесена на другой ПК или восстановлена из бэкапа в другой профиль.

- `cache.db`: если `Unprotect` или открытие БД не удались, переименовать файлы в `cache.db.unreadable-<utc>` (не удалять), создать новую пустую БД и пересканировать. Пользователь видит одно уведомление «кэш пересоздан».
- `journal.db`: так же переименовать, не удалять, и создать новую. Показать блокирующее предупреждение: история действий и привязка элементов карантина к исходным путям недоступны. Файлы в карантине остаются на диске, их можно восстановить вручную в выбранную папку. Отдельная ветка в UI «Карантин без журнала».
- Опционально в v1: экспорт ключа `journal.db`, защищённого паролем пользователя (PBKDF2/Argon2 + AES-GCM), как «ключ восстановления». В MVP не делаем.

## Последствия

- Зависимость `Microsoft.Data.Sqlite` заменяется на `Microsoft.Data.Sqlite.Core` + `SQLite3MC.PCLRaw.bundle` (версии в ADR 0006). Пакет `Microsoft.Data.Sqlite` (meta) подключать нельзя: он тянет второй нативный `e_sqlite3`, и провайдеры будут конфликтовать.
- `SQLite3MC.PCLRaw.bundle` 2.6.1 подтягивает `SQLitePCLRaw.core` 3.0.2, хотя `Microsoft.Data.Sqlite.Core` 10.0.13 объявляет `>= 2.1.13`. В spike это работает. Связку нужно закрепить версиями в `Directory.Packages.props` и покрыть smoke-тестом (`select sqlite_version()` ≥ 3.51.3, `cipher` задан, неверный ключ отклоняется).
- Строку угрозы «Утечка путей» в §11 ТЗ нужно переформулировать: «шифрование `cache.db`/`journal.db` (SQLite3MC, ключ под DPAPI), логи без путей, «Скрыть пути» в экспорте». Пометку в `paths` из §8 убрать.
- Пути в памяти процесса и в UI остаются открытыми. Шифрование at-rest это не меняет.
- Зашифрованную БД нельзя открыть внешним `sqlite3.exe` при отладке. Нужна dev-команда «экспорт расшифрованной копии» (только в debug-сборке) или CLI SQLite3MC.
- Рост зависимости от одного сопровождающего (utelle/SQLite3MultipleCiphers). Риск смягчается тем, что формат совместим с SQLCipher: можно переключить шифр на `sqlcipher` и в крайнем случае перейти на другую сборку.

## Что не проверено

- Производительность чтения на реалистичной БД (1–3 млн строк `paths`, БД больше page cache): холодный старт, обход дерева, `LIKE`. Ожидается 5–15 % накладных расходов, это не измерено.
- Какой шифр SQLite3MC выбрал по умолчанию в spike. Шифр явно не задавался, проверялся только факт шифрования.
- Поведение DPAPI после сброса пароля, пересоздания профиля, входа через Microsoft account или домен на этой машине не воспроизводилось. Сценарии взяты из документации DPAPI.
- Работа SQLite3MC при одном writer и нескольких read-only соединениях из разных процессов (UI и broker), а также при `synchronous=FULL` под нагрузкой.
- Совместимость с ARM64 и публикацией trimmed/single-file. Проверялся только win-x64, framework-dependent.
- Утечка через временные файлы (`TEMP_STORE=2` держит временные таблицы в памяти, но большие сортировки могут уходить на диск), а также через файл подкачки и crash dump.
- Стоимость `ProtectedData` измерена на одной машине с локальной учётной записью. На доменной машине вызов может быть дороже.
