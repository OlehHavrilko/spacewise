# Spacewise: сравнение подходов Codex и Claude и итоговые решения

**Дата:** 23.10.2026. **Статус:** нормативный документ. Он дополняет и уточняет [ТЗ Spacewise](ТЗ%20Spacewise.md). При противоречии приоритет у этого документа.

## 1. Итог в пяти предложениях

Оба подхода сходятся в главном: WPF на .NET 10, детерминированный executor с удалением по handle, модель без права исполнять, SQLite, кратковременный elevated broker вместо службы, MSI per-machine, честный учёт байтов на томе. Базой выбрано ТЗ Claude: оно соответствует решениям владельца о нулевой фоновой нагрузке и об автопилоте в коридоре и уже содержит требования с приоритетами, экраны и критерии приёмки. Из подхода Codex взяты пять сильных идей, которых в ТЗ Claude не хватало: защита игровых установок как целостных единиц, жизненный цикл адаптера с привязкой согласия, профили, учёт перенесённых и «обезвоженных» байтов, а также уже исправленный и проверенный обход каталогов в каркасе. Отклонены постоянный opt-in наблюдатель процессов (нарушает нулевой фон) и отдельный Apple-inspired визуальный язык (заменён Fluent-оболочкой с общими токенами). Каркас переименован в Spacewise, перенесён в корень репозитория и собран заново: 0 предупреждений, 22/22 smoke-проверки, 7/7 регрессионных сценариев, WPF smoke с кодом 0.

## 3. Где подходы совпадают

Эти решения больше не обсуждаются, они общие для обоих ТЗ:

- **Стек:** C#/.NET 10 LTS, WPF, MVVM; WinUI 3 — только при старте с нуля.
- **Измерение:** освобождённым считается только изменение свободного места тома (`GetDiskFreeSpaceExW` до и после). Неизвестный размер хранится как `null`, а не 0. Карантин и Корзина на том же томе место не освобождают.
- **Executor:** удаляет по handle с проверкой FileId и тома, без рекурсивного удаления по пути, с журналом намерений и сверкой после сбоя. Blind retry запрещён.
- **Broker:** кратковременный elevated-процесс по UAC, а не служба. Именованный канал с явной DACL, проверка клиента, только типизированные операции.
- **Системные области:** WinSxS, Windows.old, Installer, DriverStore только штатными механизмами Windows, прямое удаление файлов запрещено. `/ResetBase` — отдельная необратимая операция.
- **ИИ:** llama.cpp/GGUF в отдельном непривилегированном процессе. Кандидаты Qwen3.5-2B, Qwen3-4B-Instruct-2507, Phi-4-mini. Модель видит только агрегаты и ID фактов. Ответ ограничен грамматикой и проверяется валидатором. Имена файлов — недоверенные данные.
- **Аналитика:** «не менялось» не равно «не используется». Статусы наблюдения `ObservedActive … ConflictingEvidence` и уровни доказательности (оба ТЗ используют одну таблицу).
- **Данные:** SQLite через Microsoft.Data.Sqlite, один писатель, WAL, база только локально.
- **Поставка:** MSI per-machine, подпись всех бинарников, без trimming для WPF, Velopack не подходит из-за broker.
- **Запрещено:** чистка реестра, оптимизаторы RAM, дефрагментация SSD, «индекс здоровья ПК».

## 4. Расхождения и выбор

| Тема | Codex | Claude | Решение | Почему |
|---|---|---|---|---|
| Источник данных об использовании | Opt-in collector процессов и foreground-периодов с момента установки + исторические артефакты | Только ретроспективное чтение артефактов Windows (UserAssist, BAM, Prefetch, SRUM, лаунчеры) и USN-журнала при открытии окна | **Claude** | Решение владельца D4: закрыл окно — процессов нет. Окно наблюдения растёт за счёт снимков при каждом запуске |
| Решения ИИ | Модель только объясняет; новые предположения никогда не становятся автодействиями | Уровни L0–L3; автопилот в коридоре (категория + обратимость + уверенность + лимит) | **Claude** с ограничением Codex | Владелец хочет решения в коридоре. От Codex: модельная уверенность в коридоре только с v2, а в MVP и v1 автопилот исполняет лишь правила каталога |
| Системное обслуживание в первом релизе | Сначала переход в Settings, программный DISM после проверки | Broker с enum-операциями DISM/VSS/powercfg/pnputil | **Claude**, переход в Settings как запасной путь | Без системных источников нет «мощнее BleachBit». Если spike по операции не прошёл, UI открывает страницу Settings |
| Защита игр | `Library → InstallUnit → ResourceGroup`, `DenyGenericDescendantMutation`, ownership graph | Владелец по префиксу `InstallLocation` | **Codex** | Сильнее: защищает ассеты игры от общих правил «cache/temp/старое». См. §5.1 |
| Контракт адаптера | `Discover → Estimate → Prepare → Execute → Verify`, `SnapshotBound`/`PolicyBound` | `ICleanupAction` + подписанный JSON-каталог | **Слияние** | Каталог Claude + жизненный цикл и привязка согласия Codex. См. §5.2 |
| Профили | 7 профилей с категориями, лимитами, политикой занятых приложений | Нет, только коридор | **Codex** как пресеты коридора | Понятнее пользователю, чем ручная настройка коридора. См. §5.3 |
| Учёт байтов | `moved`, `dehydrated`, `daemon-reported`, `host delta` отдельно | То же в accounting contract | **Совпадает** | Добавлены OneDrive «Освободить место» и перенос C→D. См. §5.4 |
| Автозагрузка | Сначала переход в Settings, свой setter позже | Задачи оптимизации с откатом | **Codex** для MVP и v1 | Меньше риска сломать чужие программы. См. §5.5 |
| Сканер | Исправлен DFS по стеку приостановленных enumerator'ов, 10 002 плоских подкаталога без потерь | `FileSystemEnumerable<T>` без лишних syscalls | **Оба** | Сохраняется обход Codex (проверен), внутри него данные берутся из буфера перечисления вместо `File.GetAttributes`/`FileInfo` |
| Визуальный язык | Apple-inspired: собственные токены, спокойные поверхности | Fluent `ThemeMode=System`, Mica, NavigationView-брейкпойнты, те же токены | **Claude** | Привычное Windows-поведение и системная High Contrast. Токены Codex сохранены, HTML-прототип остаётся референсом композиции |
| Единицы | GiB в прототипе | «ГБ» в двоичных единицах, как в Проводнике | **Claude** | Цифры совпадают со свойствами диска |
| Структура решения | 11 проектов `Cleaner.Domain/Application/...`, «дробить по необходимости» | 11 проектов `Spacewise.*` | **Claude по именам, Codex по темпу** | Проекты создаются, когда в них появляется код, а не заранее |
| Оценка сроков | 6–9 месяцев, 3–4 инженера, 24–40 чел.-мес. до ограниченного релиза | MVP 10–14 недель, 2–3 разработчика | **Новая оценка для соло-разработки с ИИ-агентами**, см. §6 | Реальный состав — один владелец и агенты |

## 5. Нормативные дополнения к ТЗ (взяты у Codex)

### 5.1 Игровые установки — целостные единицы политики

- Модель данных: `Library → InstallUnit → ResourceGroup → File`. `ResourceGroup.kind ∈ {InstalledAssets, VerifiedRebuildableCache, DLC, Mods, Workshop, Saves, Settings, SharedRuntime}`.
- `InstallUnit` с состоянием `Installed` получает `DenyGenericDescendantMutation`. Никакое общее правило (temp, возраст, размер, слово `cache` в имени) не может изменить файл внутри.
- Разрешены только: узкий адаптер проверенной версии для конкретного кэша (с раскрытой ценой пересборки шейдеров или повторной загрузки), штатный перенос и удаление через лаунчер.
- Общие зависимости (redistributable, shared runtime) не удаляются, пока у них есть хотя бы один владелец.
- Состояния `Updating` и `Running` откладывают действие. `Unknown` и `ConflictingEvidence` блокируют изменение, но не анализ.
- Обязательные регрессионные сценарии: таблица из §3 отчёта Codex «Глубокая очистка» (`temp_texture.cache` внутри установленной игры, общий redistributable, устаревший manifest с модами и сохранениями).
- Приоритет: **MVP** для запрета, **v1** для адаптеров Steam.

### 5.2 Жизненный цикл адаптера и привязка согласия

```text
ICleanupAdapter.Discover(context)            -> Findings + Evidence
ICleanupAdapter.Estimate(finding, policy)    -> Estimate + Effects + Quality
ICleanupAdapter.Prepare(planItem)            -> PreparedOperation + ScopeContract
ICleanupAdapter.Execute(prepared, authz)     -> NativeOutcome
ICleanupAdapter.Verify(outcome)              -> Verified | Partial | NeedsRecheck
```

- Правило каталога (JSON с подписью Ed25519, формат из ТЗ §4.9) ссылается на `adapterId`. Произвольная команда в каталоге запрещена. Встроенный адаптер может вызвать конкретную CLI (`docker builder prune`, `dotnet nuget locals`) по абсолютному пути с фиксированной схемой аргументов.
- Каждый адаптер объявляет `scopeBinding`:
  - `SnapshotBound` — согласие распространяется на конкретный набор FileId из плана;
  - `PolicyBound` — согласие на предикаты, лимиты и проверенный контекст (например, локальный Docker daemon), с повторным preflight перед запуском.
- Автопилот (L3) допускает только `SnapshotBound` или `PolicyBound` с `automationEligible: true` в подписанном правиле.
- Обновление каталога не расширяет уже выданное согласие и коридор.
- Импорт Winapp2/CleanerML — только как «предложения» после lint, с учётом лицензий (GPL BleachBit, CC BY-SA Winapp2).

### 5.3 Профили — пресеты коридора

Профиль хранит категории, `min_age_days`, `max_bytes_per_run`, исключения, политику занятых приложений («пропустить», «ждать», «предложить закрыть») и уровень автономии. Встроенные профили: «Бережный», «Глубокое освобождение места», «Разработчик», «Игровой компьютер», «Приватность», «После удаления программ». Название профиля не отменяет защит из ТЗ §6.5 («Никогда»). Приоритет: **v1**.

### 5.4 Дополнительные виды учёта

К accounting contract из ТЗ §4.1 добавляются операции и их метрики:

| Операция | Что показывается | Чего не показывать |
|---|---|---|
| Перенос C→D (штатный для лаунчеров, выбранные папки) | «На C освобождено X, на D занято X» | Общую экономию |
| OneDrive «Освободить место» (dehydration) | «Локальная копия убрана, в облаке остаётся» | Удаление из папки синхронизации как безопасное |
| Docker prune | Отчёт daemon и отдельно изменение тома хоста | Равенство этих величин |

Предусловия OneDrive: синхронизация завершена, нет ожидающих загрузок. Приоритет: перенос и Docker — **v1**, OneDrive — **v2**.

### 5.5 Автозагрузка и фон

В MVP и v1 Spacewise показывает элементы автозагрузки (Run-ключи, папка Startup, задачи Планировщика, службы сторонних издателей) с издателем и наблюдаемой нагрузкой и открывает штатную страницу Windows для изменения, затем проверяет результат повторным чтением. Собственное отключение с откатом появляется в v2 после проверки конкретного механизма.

## 6. Дальнейшая судьба проекта

### 6.1 Рекомендуемый путь

1. **MVP без прав администратора.** Он полезен сам по себе: быстрый анализ, пользовательские и прикладные кэши (браузеры, Electron, лаунчеры, dev-кэши), измерение тома, аналитика из UserAssist и инвентаря, план, executor с карантином, журнал, советник. Это первая подписанная бета.
2. **v1 = «мощнее BleachBit».** Broker и системные источники (WinSxS, Windows.old, VSS, hiberfil, DriverStore, кэш обновлений), BAM и Prefetch, USN-инкремент, история и прогноз, локальная LLM-помощник, профили, автопилот только для правил каталога, разовая задача Планировщика.
3. **v2 = «умный».** Модельная уверенность в коридоре, MFT-сканер, SRUM, компактация VHDX, OneDrive dehydration, собственная оптимизация автозагрузки, ARM64.

### 6.2 Оценка для одного разработчика с ИИ-агентами

Оценка экспертная, пересчитывается после первых двух спринтов по фактическому темпу.

| Этап | Срок | Главный риск |
|---|---|---|
| Спринт 0 (остаток) | 1–2 недели | Spike-и: ACL Prefetch/BAM/USN без прав, POSIX rename на Win10, toast из unpackaged WPF, `IEmptyVolumeCache` |
| MVP | 4–6 месяцев | Executor и его тесты на VHDX (нельзя сжимать) |
| v1 | ещё 4–6 месяцев | Broker и безопасность IPC; нужен внешний security review |
| v2 | ещё 4–6 месяцев | Форматы артефактов Windows, качество классификатора |

ИИ-агенты ускоряют UI, парсеры и тесты. Ревью безопасности executor и broker, тесты на реальных NTFS-фикстурах и ручную проверку доступности они не заменяют.

### 6.3 Сделано в этой ревизии каркаса (спринт 0, часть 1)

- Ветки слиты в `main`. Исходные состояния сохранены тегами `baseline-codex` (каркас и ТЗ Codex) и `claude-spec-original` (ТЗ Claude до слияния).
- Репозиторий переструктурирован: код в корне (`Spacewise.slnx`, `src/`, `tests/`), документы в `docs/`.
- Проекты, пространства имён и заголовок окна переименованы `Cleaner.*` → `Spacewise.*`.
- Проверка после переименования: Release build — 0 предупреждений и ошибок; `Spacewise.SmokeTests` — 22/22; `Spacewise.Desktop.exe --smoke-test` — код 0; регрессионный режим `dotnet run --project tests/Spacewise.SmokeTests -c Release --no-build -- --regression` — 7/7, 0 ошибок.

### 6.4 Следующие задачи по порядку

1. Сканер: внутри обхода Codex брать `Attributes`/`Length` из `FileSystemEnumerable<T>` вместо `File.GetAttributes` и `FileInfo` (ТЗ FR-SCAN-001).
2. Развести покрытие на «Исключено», «Недоступно», «Не досканировано» в UI (счётчики `SkippedByPolicy` и `UnvisitedDirectories` уже есть в ядре) и ввести состояние `RootNotFound` вместо `Failed` с текстом «не найден» (FR-SCAN-002).
3. `AllocatedBytes`, `FileId`, `Links` для top-N (FR-SCAN-003).
4. MVVM + Generic Host, `IScanService`, форматирование размеров по правилу единиц.
5. Перевести smoke-harness в xUnit и добавить NTFS-фикстуры на VHDX.
6. Spike-и из §6.2.
7. SQLite `cache.db`/`journal.db`, затем каталог правил и план, затем executor.

Инвариант до шага 7: `ReadOnlyPolicy.EvaluateMutation()` всегда отказывает, кнопки удаления нет.
